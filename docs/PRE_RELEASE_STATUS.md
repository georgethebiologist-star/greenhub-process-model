# Pre-release validation status

**State: not ready for a public pre-release.** This report records the checks run during the current handover work.

**Candidate identifier:** `0.2.0-alpha.1`, matching the project's Alpha 0.2 checkpoint history. This is an internal handover label, not an authorization to distribute the package.

## Verified in this workspace

- CPython compilation completed for `api/` and `Greenhub/`.
- The frontend TypeScript check (`npm run lint`) passed after removing two stale storage-state restore calls that remained after the storage UI was removed.
- The frontend production build (`npm run build`) passed. Vite warns that the main JavaScript bundle is about 942 kB minified, above its 500 kB guidance threshold.
- The compiled frontend was started with `NODE_ENV=production`; the built page returned HTTP 200 and `/api/v1/health` returned `ok` both directly from Python and through the Node frontend proxy. The verification script stopped both services afterward.
- Frontend fallback-fixture and decision-support checks reported success.
- Local launches using `launch.ps1 -SkipInstall` and the double-click `Start GreenHub.bat -SkipInstall` wrapper reached the ready message. Direct and proxied `GET /api/v1/health` returned `status: ok`, and the UI page returned HTTP 200. A baseline scenario sent through the UI proxy completed with `validation.passed: true`; it returned 14 model warnings. Ctrl+C stopped listeners on ports 3000 and 8000.
- Python runtime and development requirement files passed pip's offline `--dry-run` resolution against the existing CPython 3.12.14 environment. This did not prove installation into a clean environment.
- The existing Python environment passed `pip check`; all 62 projects explicitly pinned by the runtime and development requirement files were installed at the declared versions. The environment also contains 41 unpinned extra packages (excluding pip/setuptools/wheel), so this check does not substitute for a fresh-environment install.
- The PowerShell launcher parsed successfully and relative Markdown links checked cleanly.

## Failed or incomplete gates

- The API boundary-mass discrepancy was traced to the modified canonical feed-composition profile, not a mass-balance calculation change. Replaying the exact API request with the committed feed profile reproduced the test's old inlet and outlet values exactly (`409.9083178971942` / `409.9083179012139 kg/h`); the current profile produces `402.0792079882833` / `402.07920799222285 kg/h` and passes Phase 7 validation. The API test now asserts the current profile's results. This confirms profile-driven provenance for this difference, but does not replace a pre-handover model snapshot or establish independent scientific validation of the updated profile.
- The updated API result test passed in isolation (`1 passed`, exit code 0). The six-file focused selection passed all 66 collected tests: pytest reached `[100%]` and returned code 0. The wrapper process remained open after pytest returned; process inspection showed the Python runner had exited, leaving a shell/tool session artifact rather than a live test process. The run reported dependency deprecation/resource warnings and BioSTEAM cost-correlation warnings.
- The last complete full-suite result collected 1,075 tests and reached 100% in 974 seconds: 1,074 passed and one failed. The sole failure is `tests/test_api_server_concurrency.py::test_health_like_http_request_is_served_while_another_request_is_waiting`; its worker did not signal within the test's one-second timeout in this restricted loopback environment. The same test passed when run with local-network permission in an earlier verification. The two governance tests that failed in the preceding full run now pass in isolation. Pytest reported no setup errors. The run emitted dependency deprecation/resource warnings and BioSTEAM cost-correlation warnings.
- The FAIR catalog generator now supports source sidecars that identify assets through `source_file`, `source_asset_path`, or `source_asset`, carries sidecar source identifiers into catalog linkage, resolves local manifest rows from the nearest ancestor package directory, and records maturity separately from activation state. The catalog CSV/JSON were regenerated (869 assets; 923 input records; 627 source-linked assets; 493 assets with DOI; 249 assets without a source-register link). The workbook snapshot tabs were also refreshed and verified: `FAIR_Catalog` has 869 asset rows and `Master_Inputs` has 923 normalized records.
- A complete before-and-after baseline comparison remains unavailable. The working copy already contained extensive source, test, input-data, and research-artifact changes before handover edits began; no clean pre-change simulation snapshot was available.
- A clean installation on a fresh computer has not been run. The launcher test skipped installation; the environment could not reach the package registry during this session.
- macOS and Linux instructions are provided but were not validated. Optimization alternatives, complete exports, every process route, and all TEA/LCA boundaries have not been fully exercised in this handover run.
- The Python process and frontend package versions are now pinned, but GreenHub code ownership, Spaak brand-asset permission, and source-data redistribution rights remain unresolved; see [third-party notices](THIRD_PARTY_NOTICES.md).
