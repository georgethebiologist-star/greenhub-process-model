# Developer guide

Start with the [architecture guide](architecture.md), [data reference](input_data_reference.md), [scientific assumptions](scientific_assumptions.md), and [model limitations](model_limitations.md). Keep process simulation separate from post-simulation TEA and LCA, preserve scenario IDs and data provenance, and record whether values are measured, literature-derived, estimated, or assumed.

## Common changes

| Change | Authoritative location | Checks and dependencies |
| --- | --- | --- |
| Feedstock composition and availability | Start with `Greenhub/data/greenhub_feed_inputs.xlsx` (`FeedMeasurements`, `GrassMeasurements`, `MonthlyMass`, and `GrassAvailability` sheets); trace detailed evidence under `Greenhub/data/Pre-treatment/Feedstock/`. | Keep wet/dry basis, units, month/site, source IDs, and quality class together. Check workbook loading, feed-profile, and provenance tests. |
| Default parameters and editable controls | `Greenhub/parameters/registry.py`, `models.py`, `resolver.py`, `overrides.py`, and `editable_registry.py`; detailed source records under `Greenhub/data/advanced_model/`. | Preserve parameter IDs and override precedence. Check validation, serialization, service defaults, and the relevant route tests. |
| Literature or experimental datasets | Stage-specific folders under `Greenhub/data/`, with `.source.json` sidecars, `source_register.csv`, and dataset manifests. | Update source and missing-data registers. Keep measured, literature, proxy, estimated, and assumed values distinguishable; do not activate a dataset just by adding a file. |
| Process equations, efficiencies, unit operations, and routes | Unit calculations in `Greenhub/phase*_units.py` and `Greenhub/units.py`; route factories in `Greenhub/systems.py`, `Greenhub/phase7_systems.py`, and `Greenhub/integration.py`; equations in `Greenhub/scientific_equations.py`. | State the stream basis and units. Add unit and boundary tests, then test the integrated route and mass/element balances. Preserve scenario and unit IDs. |
| Equipment/consumable costs and TEA | `Greenhub/tea_costs.py`, `Greenhub/tea_finance.py`, `Greenhub/tea.py`, registered cost inputs, and the source inventory generator `scripts/build_economic_inventory.py`. | Check currency and reference year, size/capacity basis, units, and finance assumptions; compare the same baseline and report unsupported correlations. From the project root, run `.venv\\Scripts\\python.exe scripts\\build_economic_inventory.py` to regenerate the CSV/JSON source inventory in `Greenhub/results/`. |
| LCA inventory and impact factors | `Greenhub/lca_inventory.py`, `Greenhub/lca.py`, `Greenhub/application/lca_service.py`, `docs/lca_inventory.md`, and source data. | Check functional unit, boundary, allocation, factor source/year, and missing flows. Do not present a partial climate subtotal as a complete LCA. |
| Optimization objectives, constraints, and KPIs | `Greenhub/application/decision_support_service.py`, `decision_batch_jobs.py`, `Greenhub/decision_support_examples.py`, and `Greenhub/phase*_metrics.py`; frontend projection helpers are in `frontend/src/data/decisionSupport.ts`. | Check request/result contracts, feasibility, deterministic replay, units, and scenario parity. Test both the service and API contract; do not move scientific calculations into the UI. |
| API endpoints | `api/app.py`, `api/server.py`, and request/result contracts in `Greenhub/application/contracts/`. | Keep transport logic thin; update OpenAPI export and `tests/test_api_v1.py`; preserve stable versioned response fields and structured errors. |
| Frontend screens and charts | `frontend/src/App.tsx`, `frontend/src/components/`, `frontend/src/data/apiClient.ts`, and result normalization helpers. | Use API result fields and warnings; avoid duplicating scientific calculations. Run `corepack pnpm lint`, relevant fallback/decision checks, and the production build from `frontend/`. |
| Reports and exports | `Greenhub/application/export_service.py`, `plot_service.py`, `result_service.py`, `Greenhub/*reporting*.py`, and `api/app.py`. | Preserve run IDs, units, provenance, assumptions, warnings, and machine-readable contracts. Check `tests/test_reporting_io.py`, API export tests, and the target format. |

Configuration and registered input data are appropriate for changing values within an established model. Changes to equations, calculation order, balances, API contracts, or UI behavior require source changes and corresponding verification. Consult the stage-specific methodologies and checkpoint/release notes in `docs/` before modifying an experimental pathway.

## Local checks

From the project root, install test dependencies with `.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`, then run focused tests with `.venv\Scripts\pytest.exe tests\<relevant_test>.py -q` on Windows. Examples include `test_phase7_balance_and_utilities.py` for nutrient recovery boundaries, `test_tea_service.py`, `test_lca_service.py`, `test_api_v1.py`, and `test_reporting_io.py`. Run the full model suite with `.venv\Scripts\pytest.exe -q` when practical. Frontend commands use the project's pinned package manager: run `corepack pnpm lint`, `corepack pnpm check:fallback`, `corepack pnpm check:decision`, or `corepack pnpm build` from `frontend/`. Record commands, outcomes, and pre-existing warnings in the release handover. Do not describe an unexecuted check as passed.
